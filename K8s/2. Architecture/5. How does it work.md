# What is kubectl.

kubectl functions as a client application that communicates with the Kubernetes API server. This client-server relationship is fundamental to how Kubernetes works.

## kubectl as a Client

kubectl serves as:

1. **API Client**: It translates human-readable commands into API requests that the Kubernetes API server can understand
   
2. **Authentication Handler**: It manages your credentials and authentication tokens for secure API access
   
3. **Request Formatter**: It structures requests according to Kubernetes API specifications
   
4. **Response Interpreter**: It parses JSON/YAML responses from the API server into user-friendly formats

## The Client-Server Architecture

Your notes accurately describe the client-server interaction:

```
User → kubectl (client) → API Server (server) → etcd (database)
```

When you run `kubectl get pods`, this client-server pattern happens exactly as your notes outline:
1. kubectl prepares credentials
2. Sends HTTP request to API server
3. API server authorizes the request
4. Data is retrieved from etcd
5. Response is sent back to kubectl
6. kubectl formats and displays the results

## Why This Matters

Understanding kubectl as a client is important because:

1. **Multiple Clients**: The Kubernetes API can be accessed by other clients too (dashboard UI, custom scripts, CI/CD tools)

2. **Cluster Administration**: You can control access to the cluster by managing client credentials

3. **Automation**: You can write scripts that use kubectl or directly call the API

4. **Troubleshooting**: Connection issues are often between the client (kubectl) and server (API server)

This client-server relationship is why you need to configure kubectl with the correct server address (192.168.10.100:6443 in your case) and authentication details through the kubeconfig file.



# What Happens When You Run `kubectl get pods`

When you run the command `kubectl get pods`, a series of operations happen behind the scenes:

## The Process Flow

1. **Authentication**: `kubectl` uses your credentials from the kubeconfig file (~/.kube/config) to authenticate with the API server at 192.168.10.100:6443

2. **API Request**: `kubectl` sends an HTTP GET request to the API server endpoint:
   ```
   GET /api/v1/namespaces/default/pods
   ```

3. **Authorization**: The API server verifies you have permission to list pods in the target namespace

4. **Data Retrieval**: The API server queries its etcd database for information about all pods in the specified namespace

5. **Response Processing**: The API server sends back JSON data about the pods' status, which `kubectl` formats into a table

6. **Output Display**: `kubectl` shows you the pods with columns for name, ready status, status, restarts, and age


# Communication Between API Server and Kubelet During Pod Lifecycle

## Pod Creation Process

When creating and managing pods, the API server and kubelet interact in a coordinated sequence:

### 1. Pod Creation Request Handling

1. **API Server Receives Request**: 
   - kubectl (or another client) sends a request to create a pod
   - API server validates the request against schema
   - Request is authenticated and authorized

2. **API Server Stores Pod Definition**:
   - API server saves the pod definition to etcd
   - Pod is marked with status "Pending"

### 3. Scheduler Involvement 

1. **Scheduler Watches for New Pods**:
   - Scheduler (a control plane component) monitors the API server
   - It notices the new "Pending" pod without a node assignment

2. **Node Selection**:
   - Scheduler evaluates which node has sufficient resources
   - Updates the pod definition with the selected node name
   - API server saves the updated pod definition to etcd

### 4. Kubelet Takes Action

1. **Kubelet Monitors API Server**:
   - Each node's kubelet constantly watches the API server
   - Kubelet on the selected node discovers a pod assigned to it

2. **Pod Creation Operations**:
   - Kubelet downloads the pod specification
   - Ensures necessary images are available (pulls if needed)
   - Creates containers through the container runtime (Docker/containerd)
   - Allocates required resources (CPU, memory)

3. **Status Updates**:
   - Kubelet sends status updates to the API server
   - Pod state changes from "Pending" → "ContainerCreating" → "Running"
   - API server updates the pod's status in etcd

## After Pod Creation

### 1. Ongoing Health Monitoring

1. **Kubelet Continuous Monitoring**:
   - Kubelet performs regular health checks on the pod's containers
   - Executes liveness/readiness probes if configured
   - Monitors resource usage

2. **Status Reporting**:
   - Kubelet periodically reports pod status to the API server
   - Updates include container state, resource usage, and health

### 2. Pod Lifecycle Management

1. **API Server as Source of Truth**:
   - When changes are made to pod definitions, API server stores them in etcd
   - Kubelet receives updated specifications and reconciles actual state

2. **Termination Process**:
   - If pod deletion is requested, API server updates pod status to "Terminating"
   - Kubelet sees the update and begins graceful shutdown
   - Containers receive SIGTERM, followed by SIGKILL if needed
   - Kubelet reports completion to API server

### 3. Self-Healing Actions

1. **Container Failures**:
   - If a container crashes, kubelet restarts it according to restart policy
   - Reports the restart event to the API server

2. **Node Problems**:
   - If a node fails, the API server removes pod assignments
   - Scheduler reassigns pods to other nodes
   - Kubelets on those nodes create new instances

This communication cycle ensures that pods are created, monitored, and maintained according to their specifications, with the API server acting as the central coordination point and kubelet as the node-level executor.



# Kubelet's Communication Protocol with API Server

Kubelet uses **HTTP/HTTPS with WebSockets** to watch the Kubernetes API server for pod assignments and updates.

## The Watch Protocol Details

1. **Initial Connection**:
   - Kubelet establishes an HTTPS connection to the API server
   - It authenticates using a client certificate (kubelet.crt and kubelet.key)

2. **Watch Request**:
   - Kubelet initiates a watch request using the Kubernetes API with a specific resource version
   - The request format is:
     ```
     GET /api/v1/pods?watch=true&fieldSelector=spec.nodeName=<node-name>&resourceVersion=<version>
     ```

3. **Long-Lived Connection**:
   - The connection is upgraded to a WebSocket for efficient streaming
   - This creates a persistent connection that stays open

4. **Server-Sent Events**:
   - The API server sends events over this connection whenever relevant changes occur
   - Events include pod assignments, updates, and deletions

5. **Efficient State Tracking**:
   - Kubelet maintains a local cache of pod states
   - It only receives incremental updates rather than repeatedly polling
   - Each update includes a resourceVersion to track state consistency

## Benefits of the Watch Protocol

- **Real-time Updates**: Kubelet learns about new pod assignments immediately
- **Reduced Network Traffic**: No need for frequent polling
- **Efficient Resource Usage**: Only processes changes, not full state
- **Connection Resilience**: Automatically reconnects if the connection is lost

This watch mechanism is central to how Kubernetes maintains eventual consistency between the desired state (stored in etcd) and the actual state (managed by kubelet on each node).



# When is /etc/kubernetes Folder Created?

The `/etc/kubernetes` directory is created during the execution of `kubeadm init`. This happens as one of the first steps when initializing your Kubernetes control plane.

## Creation Timeline

Looking at your installation script:

1. First, you set up prerequisites (swap off, modules, sysctl settings)
2. Then you install the required packages (kubelet, kubeadm, kubectl, containerd)
3. **Then you run `kubeadm init`**, which creates `/etc/kubernetes`

```bash
sudo kubeadm init --control-plane-endpoint=192.168.10.100 \
                 --apiserver-advertise-address=192.168.10.100 \
                 --pod-network-cidr=192.168.0.0/16
```

## What Gets Created in /etc/kubernetes

During `kubeadm init`, several important files and directories are created:

1. `/etc/kubernetes/manifests/` - Contains static pod definitions for the control plane:
   - kube-apiserver.yaml
   - kube-controller-manager.yaml
   - kube-scheduler.yaml
   - etcd.yaml

2. `/etc/kubernetes/pki/` - Contains all the certificates and keys
   - Certificate Authority (CA) files
   - API server certificates
   - Service account keys
   - etc.

3. `/etc/kubernetes/admin.conf` - kubeconfig file for the admin user

4. Other configuration files like:
   - `/etc/kubernetes/kubelet.conf`
   - `/etc/kubernetes/controller-manager.conf`
   - `/etc/kubernetes/scheduler.conf`

## Worker Nodes

On worker nodes, the `/etc/kubernetes` directory is created during `kubeadm join` execution, but with a much simpler structure - only containing files needed for the kubelet to connect to the API server.





- Namespace
- Pod
- Deployment
- Service
- Secret
- Volume
- StorageClass
- configmap
- ingress
